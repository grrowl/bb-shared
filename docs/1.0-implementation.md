# Local gateway implementation

Implemented 2026-09-08 following the design review. The review records the old
behavior; this document records the resulting implementation.

## Delivered

- A transport-only Worker with one pairing secret, a stable versioned identity,
  protocol validation, and HTTP/WebSocket relay through a Durable Object.
- A restricted local guest gateway as the sole tunnel destination. It resolves
  invitations and sessions locally, validates route/method access, strips owner
  credentials, shapes BB responses, and filters realtime messages.
- Multiple encrypted connection records, explicit default hostname, deploy or
  register workflows, and removal without claiming to delete Cloudflare resources.
- Registration checks identity, rejects duplicate relay aliases, authenticates
  the tunnel, and verifies a gateway-generated HMAC readiness proof before saving.
  Readiness probes also check the actual BB upstream. Reconnecting never remains
  Ready. Unknown relay protocols are reported as incompatible.
- Encrypted opaque browser sessions union current invitation grants. A write
  grant wins over read while valid. Revocation removes only its contribution;
  HTTP streams and sockets close on grant changes and reconnect under current scope.
- Invitations can be saved before any connection exists. URLs remain absent until
  a default hostname is available; no placeholder URLs are copied. Permissions
  are portable across registered connections rather than bound to DNS names.
- Thread popover with hostname/status, optional audience labels, read/write grants,
  invitation copying, and connection management.
- Query-only invitation redemption into a secure host cookie, clean redirects,
  and no legacy token-in-path or old Worker/OAuth registry compatibility.
- Build-time relay compilation embedded in the plugin server artifact; no runtime
  Wrangler invocation, source-tree lookup, Cloudflare SDK, or edge BB plugin token.
- Transport bounds on stream counts, buffered bodies, frame metadata, deadlines,
  and pending WebSocket data; logs exclude invitation query strings.

## Deliberate boundaries

An invitation is a bearer credential, not authenticated personal identity. All
registered relays can transport valid invitations to this instance. Relays still
terminate TLS and see guest traffic. Local policy prevents a relay connection
credential from becoming unrestricted owner API access.

Write invitations send text messages using the owner's existing thread execution
policy. File/image attachments, local-file mentions, model/permission overrides,
and impersonating another thread are excluded. The gateway projects request
bodies to accepted text input and send mode rather than forwarding arbitrary
owner-only execution options.

A browser session expires 30 days after its last invitation redemption. Expired
sessions and revoked grants do not contribute access. Storage is bounded below
BB's KV size limit; the oldest sessions are evicted when needed and guests must
reopen an invitation. Local cookies do not need clearing to enforce revocation.

Two simultaneous *first* redemptions without an existing cookie can race to
establish separate sessions. Sequential first opens work, and additions to an
established session are serialized. Avoiding that first-open race would require
an extra browser handshake; it is not silently presented as solved.

The v1 relay accepts a guest WebSocket upgrade before the local gateway accepts
its upstream socket. Unauthorized sockets close rather than returning an HTTP
401 during the WebSocket handshake. They receive no authorized guest frames.
HTTP 401/403/502/503 responses preserve their distinction.

A relay supports one active BB tunnel. Register a custom domain as its canonical
hostname; registering two aliases as separate connections is rejected. Remove
and re-register to change the canonical hostname. Old copied links cannot be
repaired if their domain is deleted. Restoring only a relay hostname does not
restore lost local invitation/session records or their device key.

The Worker is intentionally small and stable, but transport vulnerabilities or
future incompatible protocols can still require an update. Claiming does not
provide BB with authority to deploy that update to a Cloudflare account.

## Verification

Final checks: 252 plugin tests passed (one platform-specific test skipped),
24 Worker tests passed, typechecks passed, and plugin build passed.

- Plugin tests include the real SDK fake host, strict JSON RPC transport, actual
  local HTTP/WebSocket servers, encrypted persistence/reload, mutation rollback,
  gateway disposal, session union/revocation, and pure policy/filter coverage.
- Worker tests run in actual `workerd` via Miniflare. A full-stack network test
  joins Worker → actual tunnel client → guest gateway → mock BB HTTP/WebSocket
  server, including pairing, readiness, cookies, scope and realtime revocation.
- A clean Chromium browser loaded this existing thread through a temporary local
  gateway against the running BB 0.42.1 app. The transcript rendered with no
  JavaScript errors. The environment metadata request was correctly denied;
  plugin contributions and thread tabs receive safe empty responses.
- Typechecks cover plugin, Worker runtime, and integration-test environments.
  The plugin builds both frontend and backend with the relay artifact embedded.

No production Worker was deployed or claimed, and the installed plugin was not
replaced during this implementation. Remaining release validation is an external
network guest session with a newly deployed/claimed Worker, plus real sleep/wake
and long-running reconnect behavior. The tests and live local browser check do
not claim those Cloudflare lifecycle cases were exercised.
