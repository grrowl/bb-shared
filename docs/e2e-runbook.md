# bb-shared — end-to-end smoke-test runbook

Manual walk-through of the full bb-shared flow, from a clean plugin install to
guest revocation. This is the deliverable of issue
[17](../.scratch/v0/issues/17-e2e-smoke.md) and the last v0 ticket.

Everything below is cross-checked against the delivered code and the resolved
ticket answers under `.scratch/v0/issues/`. Where the SPEC or a ticket's prose
drifts from what actually shipped, it is called out inline under a **⚠ Drift**
callout rather than papered over — read those before running, they change what
you should expect to see.

> **Do not treat this as automated coverage.** It is a manual runbook; a real
> run needs Cloudflare egress (the deploy PoW hits `api.cloudflare.com`) which
> the `mactom` agent sandbox does not have. Run it from a machine with open
> egress. Automate later only if it earns its keep (per the ticket).

### Plugin identity — read this before anything else

The npm package is `bb-plugin-shared`, so **bb derives the runtime plugin id as
`shared`** (the `bb-plugin-` prefix is stripped). This is confirmed by issue
04's own verification: `bb plugin install` reported **`shared@0.1.0 running`**,
and the scaffold's sanity-check curl hits `/api/v1/plugins/**shared**/rpc/…`.

> **✅ Plugin id `shared` — reconciled (ticket 22).**
> The plugin mounts under **`shared`** (bb strips the `bb-plugin-` prefix from
> package name `bb-plugin-shared` — confirmed by 04's `shared@0.1.0 running`).
> Every URL path in the worker and plugin now uses `shared`: the per-request
> authz call is `GET /api/v1/plugins/shared/http/authz` and the nav panel is
> `/plugins/shared/tokens`. `bb-shared` remains the project/repo name only.
>
> Earlier drafts (SPEC + issues 06, 10, 16) wrote these paths as `bb-shared`,
> which would have made the worker call a non-existent authz endpoint → every
> guest request fails authz closed → **403**, nothing works. Ticket 22 fixed
> all such references. Sanity-check the live mount before the walk-through:
>
> ```
> bb plugin list                 # expect: shared@0.1.0 running
> curl -sS -X POST http://127.0.0.1:38886/api/v1/plugins/shared/rpc/listTokens \
>      -H 'content-type: application/json' -d 'null'
> curl -sS "http://127.0.0.1:38886/api/v1/plugins/shared/http/authz?token=x&path=/system/config&method=GET" \
>      -H "authorization: Bearer $(bb plugin token shared)"
> ```

### Env / config

- No env vars are required of the operator for the plugin itself — the two
  secrets are generated by the plugin at deploy time:
  - **`AUTHZ_TOKEN`** — bb's built-in per-plugin token (`bb.sdk.plugins.token`),
    planted on the worker as a `secret_text` binding (issue 07).
  - **`TUNNEL_SECRET`** — 32-byte CSPRNG handshake secret, minted per deploy,
    persisted in `bb.storage.kv`, planted on the worker and used by
    `SharedTunnel` to dial `/__tunnel` (issues 07 + 14).
- **Worker deployment record persists** in `bb.storage.kv` (SPEC calls this
  "PluginSettings"; the concrete durable surface is `bb.storage.kv` — issue 07).
  This is the one narrow exception to v0's in-memory-only stance. Token/share
  state stays purely in memory.

## Setup

All commands run from a checkout of this repo.

### 1. Install plugin

```bash
cd plugin/
npm install                 # first time only — SDK + shadcn deps + vendored tunnel pkgs
bb plugin build .           # produces dist/{server,app}.{js,…} + meta.json
bb plugin install . --yes   # registers as a path source; runs from src
bb plugin list              # expect: shared@0.1.0 running   (id = "shared")
```

Iterative development (watches sources, rebuilds + reloads on save):

```bash
bb plugin dev .
```

The frontend bundle is picked up on the next SPA reload.

### 2. Verify the plugin loads

- **Backend / RPC alive** — from a bb terminal:

  ```bash
  curl -sS -X POST http://127.0.0.1:38886/api/v1/plugins/shared/rpc/listTokens \
       -H 'content-type: application/json' -d 'null'
  # healthy plugin → { "ok": true, "result": [] }   (empty token list on a fresh load)
  ```

- **Share button in the thread header** — open any thread in the bb SPA. A
  **Share** icon-button (the `Link` icon, `experimental_threadHeaderAction`
  from issue 15) appears at the left of the thread-header action row. The
  command palette also carries **"Share this thread"** (available whenever a
  thread is open).

- **Nav panel** — the token management console is reachable at the plugin nav
  panel **`tokens`** (title "Shared threads"), which resolves to
  **`/plugins/shared/tokens`** (issue 04 registered `path: "tokens"` under the
  `shared` plugin; SPEC/16 use the same id after ticket 22). Verify by clicking
  the panel entry.

`bb plugin logs shared` streams `bb.log` output from `server.ts` if anything
misbehaves. `bb plugin remove shared` tears the install back down.

## Deploy worker

The worker is **not** deployed at install time. Deployment is **lazy** — it
fires on the first `mintToken` (issue 07's `lifecycle.ensureDeployed()` is
awaited inside `mintToken`; SPEC says "on first `openShareDialog` or
`mintToken`, whichever comes first" — as shipped it is `mintToken`).

⚠ **Drift note.** SPEC says the deploy can also trigger on `openShareDialog`.
As delivered, only `mintToken` awaits `ensureDeployed()`. Opening the share
popover alone does **not** deploy; minting does. Expect the first mint to be
the slow one.

### What happens on first mint

1. **PoW challenge + provision** — `POST /provisioning/previews/challenge`,
   solve the SHA-256 checkpoint chain (`k*g ≤ 64,000,000` iterations), then
   `POST /provisioning/previews`. Returns an anonymous account + scoped
   `apiToken` + a `claim` (`{ token, url, expiresAt }`).
2. **Bundle + upload** — the `worker/` tree is bundled
   (`wrangler deploy --dry-run --outdir`) and uploaded via the `cloudflare` SDK
   (`workers.scripts.update` + `workers.subdomains.get`), with the `TUNNEL_DO`
   Durable Object binding, the `TUNNEL_SECRET` + `AUTHZ_TOKEN` secret bindings,
   and the first-deploy DO migration (`new_classes: ["TunnelDO"]`).
3. **Tunnel up** — `SharedTunnel` dials `wss://<worker>/__tunnel?v=1` with
   `Authorization: Bearer <TUNNEL_SECRET>`; the worker's `TunnelDO`
   constant-time-compares and holds the single active socket.

### Expected latency

Per spike 01 (`research/cf-temp-deployments.md`): CF advertises "live worker in
seconds." The variable cost is the **proof-of-work** — up to ~64M SHA-256
iterations, low single-digit seconds on a modern laptop. Script upload after the
account exists is a normal PUT (sub-second). DO cold-start on first guest invoke
adds ~50–100 ms. **Net: seconds, PoW-dominated.** Not benchmarked against a real
deploy (no CF egress in the build sandbox).

### Status / expected artifacts

- **`getWorkerStatus` RPC** returns `{ url?, state, healthy, tunnel?, fault? }`.
  Provisioning `apiToken` and the tunnel secret never cross the RPC boundary.
- **Nav-panel worker-status pill** (issue 16) renders this: "Worker not
  deployed" before first mint, healthy/unhealthy once live, "unreachable" on a
  non-stub rejection. It also live-refreshes on the `worker-changed` realtime
  channel.
- **URL shape** — `https://bb-shared-worker.<subdomain>.workers.dev` (script
  name `bb-shared-worker` from `wrangler.toml`).
- **Guest URL** returned by `mintToken` (after `addShare`):
  `https://bb-shared-worker.<sub>.workers.dev/{token}/projects/{p}/threads/{t}`.
- **`claim.url`** — a bearer credential surfaced only in the owner nav panel as
  a "Claim this worker" link (via `navigate.openUrl`, never rendered as raw
  copyable text). **Never send it to a guest, never log it** (SPEC + spike 01).

### Health / liveness

`GET https://<worker>/` must return exactly **`401 { "error": "token_missing" }`**
to identify a live worker; a Cloudflare 404 HTML page is not healthy. The plugin
checks saved workers periodically even without shares. Failure retains the
record as **Offline** and retries; it never creates a replacement automatically.
Only the owner-only **Recreate worker** action provisions a new endpoint. A new
hostname means previously copied links continue to target the old worker.

## The smoke walk-through

Two browsers: **Owner** (your normal bb session) and **Guest** (incognito / a
clean profile, no bb cookies). For each step: the action, the expected result,
and the failure indicator.

### 1. Install plugin — Share button present

- **Action:** complete **Setup** above; open a thread as Owner.
- **Expect:** `bb plugin list` shows `shared@0.1.0 running`; the **Share** icon
  is in the thread header; the palette has "Share this thread".
- **Failure:** no Share icon → app bundle didn't load (rebuild + reload SPA);
  RPC curl returns `not implemented` for a method other than `getWorkerStatus`
  → an unfilled handler (all CRUD is implemented per issues 05/06; only
  `getWorkerStatus` depends on 07 being present).

### 2. Mint a `write` token and copy the URL

- **Action:** Owner clicks **Share → "Mint new share"**, toggles perm to
  **write**, confirms. The popover (issue 15) calls `mintToken` then `addShare`
  for the current thread in sequence, writes the returned guest URL to the
  clipboard, and flashes a status line. (This is the first mint → the worker
  deploys now; expect the seconds-scale PoW delay.)
- **Expect:** clipboard holds
  `https://bb-shared-worker.<sub>.workers.dev/{token}/projects/{p}/threads/{t}`;
  the worker-status pill flips to healthy; a token card appears in the nav panel
  with one `write` share row.
- **Look for:** the token label is an auto-generated verb-noun (e.g.
  "brave-otter"). The mint is what deploys the worker — if the pill stays
  "not deployed" and no URL lands, the deploy failed (see Troubleshooting).
- **Failure:** mint hangs → PoW/egress problem; mint errors → CF provision/
  upload failure surfaced in `bb plugin logs shared`.

### 3. Open the URL as Guest (incognito)

- **Action:** paste the URL into an incognito window.
- **Expect — chrome scoped down.** Verify each element specifically:
  - **Sidebar shows ONLY the shared thread** — `sidebar-bootstrap` is filtered
    to the token's shares; projects with no share are dropped entirely (not just
    their threads), `personalProject` is replaced with an inert empty stub
    (issue 09).
  - **Settings hidden** — chrome shim hides `[aria-label^="Settings"]` (prefix
    match: bb appends `(⌘,)` when a shortcut is bound).
  - **Extensions / plugin-nav hidden** — `[data-testid="plugin-nav-sidebar-items"]`
    (a `data-testid`, **not** a CSS class) is hidden; and `/api/v1/plugins`
    returns `{ plugins: [] }` so no guest plugin frontends load at all.
  - **New-thread hidden** — `[aria-label^="New thread"]` (prefix match) and
    `[data-testid="app-sidebar-primary-actions"]` hidden.
  - The shim sets `document.documentElement.dataset.bbGuest = "1"` and injects a
    `<style>` scoped to `[data-bb-guest]` (issue 12). Confirm the `data-bb-guest`
    attribute is present on `<html>` in the guest DOM.
- **Expect — transcript visible.** The thread's transcript renders live.
- **Look for:** the sidebar thread shows the raw **`thread_id`**, not a friendly
  title — see Known limitations.
- **Failure:** if Settings/Extensions/New-thread are still visible, the shim
  didn't fire → check the guest response is `text/html` and `data-bb-guest` is
  set. If the sidebar shows extra threads/projects → response filter or authz
  scope wrong (and re-check the plugin-id drift above — a mismatched authz mount
  fails closed, but a mis-scoped one leaks).
- **Hard-navigation lock-outs:** manually visiting `/{token}/settings`,
  `/extensions`, `/tools`, `/hosts` serves a tiny HTML that `location.replace`s
  back to `/{token}/` — the SPA never mounts those routes (issue 10).

### 4. Guest sends a message → appears in Owner's view

- **Action:** Guest types a message and sends (perm is `write`).
- **Expect:** `POST /api/v1/threads/{t}/send` is allowed (in scope + `write`);
  the message lands in the thread and the **Owner** sees it. Guest-typed input
  appears as ordinary user input — **no attribution** distinguishing it.
- **Failure:** send returns `403 { error: "scope" }` → the token's share for
  this thread is `read`, or authz denied (check plugin-id drift). 

### 5. Owner sends a message → Guest sees it (realtime)

- **Action:** Owner sends a message in the same thread.
- **Expect:** the Guest sees it appear **without reload**. The guest's WS
  receives `changed`/`thread` frames for in-scope thread ids (issue 11's
  `filterServerFrame` forwards them); `thread:output`/`thread:changed`
  equivalents scoped to the allowed thread pass the filter.
- **Failure:** Guest doesn't update live → WS bridge not forwarding. Check the
  guest socket is connected and that the thread id is in the socket's scope (the
  scope is captured at WS-upgrade time — see the realtime caveat in step 6).

### 6. Add a second thread to the same token as `read`

- **Action:** Owner opens a second thread, **Share → "Add to `<label>` (read)"**
  (or add the share from the nav panel). This calls `addShare(token, thread2,
  project, "read")`.
- **Expect — owner side, live:** the **owner's** nav panel and share popover
  update **without reload** — both subscribe to the `tokens-changed` realtime
  channel via `useRealtime` and refetch (issues 15/16). The new row shows a
  `read` perm chip.
- **Expect — guest side:**
  - **View allowed:** navigating the Guest to thread 2 renders its transcript.
  - **Send blocked:** a send attempt returns **`403 { error: "scope" }`** (perm
    is `read`; the mutation gate requires `write`). The SPA send affordance may
    still be visible — the guarantee is the 403, not a disabled button.

> **⚠ Drift — "sidebar updates without reload" is owner-side, not guest-side.**
> The ticket's step 6 says the sidebar updates without reload "via `useRealtime`
> on `tokens-changed`." That hook lives in the **plugin frontend**, which is
> **suppressed for guests** (`/api/v1/plugins` → `[]`). So it updates the
> **owner's** panel, not the guest's sidebar. On the **guest** side, the sidebar
> comes from `sidebar-bootstrap` (fetched on load) and the WS scope is **fixed
> at socket-upgrade / authz time** (issue 11 reads `ctx.scope` once). A share
> added mid-session therefore does **not** auto-appear in the guest's sidebar —
> the guest must **reload** (or reconnect) to pick up the new thread. The
> newly-in-scope thread's WS frames also won't flow on the already-open socket
> until reconnect. Test the guest-side by reloading; don't expect a live sidebar
> pop-in. Flagged for v0.1.

### 7. Remove one share → Guest can no longer see that thread

- **Action:** Owner removes the thread-2 share (per-row remove → `removeShare`).
- **Expect:** any **new** guest request for thread 2 is denied — authz drops it
  from scope, so `GET /threads/{t}/*` → `403 { error: "scope" }` (API) or `404`
  (SPA/HTML), and out-of-scope WS `changed` frames are dropped. On the next
  guest **reload**, thread 2 is gone from the sidebar.
- **Look for / honest nuance:** enforcement is **pull-based**, at request time.
  A transcript already rendered in the guest's open tab is **not wiped** — issue
  11 deliberately drops the now-out-of-scope `subscribe` frame silently ("stale
  UI beats a disconnect loop when a share is revoked mid-session") rather than
  force-closing. So "can no longer see" means: no new data, and gone on reload —
  **not** an instant on-screen removal. Verify by reloading the guest.
- **Failure:** guest can still **fetch** thread 2 after removal → authz not
  reflecting the mutation (should be immediate — authz reads live store state).

### 8. Delete the whole token → Guest is booted (both threads)

- **Action:** Owner deletes the token (nav-panel delete behind an `AlertDialog`
  confirm → `deleteToken`).
- **Expect:** the token no longer resolves — `findByRawToken` → null, so authz
  returns `allowed: false, reason: "unknown token"` for **every** request. Every
  new guest request → `403` (API) / `404` (SPA); a WS reconnect fails authz.
  On the guest's next reload the whole session is dead.
- **Honest nuance (same as step 7):** there is **no proactive socket teardown**
  on delete in v0. A guest sitting on an already-loaded tab keeps seeing the
  last-rendered content until they navigate, reload, or the socket drops and
  fails to re-authorize. "Booted" = every fresh request denied immediately, not
  a live eviction. Verify by reloading the guest and by attempting a fresh
  action — both should fail.
- **Failure:** guest can still load a thread after delete → token still resolving
  (stale store) or authz mount mismatch masking the deny.

## Verification checklist

- [ ] Sidebar shows **only** shared threads (issue 09 `filterSidebarBootstrap`;
      bare projects dropped, `personalProject` stubbed).
- [ ] Settings / Extensions / New-thread chrome hidden — via the chrome shim
      (issue 12) using: `[data-testid="app-sidebar-primary-actions"]`,
      `[aria-label^="Settings"]`, `[data-testid="plugin-nav-sidebar-items"]`,
      `[aria-label^="New thread"]`, all under `[data-bb-guest]`.
- [ ] Guest views transcript (thread in scope).
- [ ] Realtime works **owner → guest** (step 5) and **guest → owner** (step 4).
- [ ] **Write** perm: guest send appears in owner's view (step 4).
- [ ] **Read** perm: guest send returns `403 { error: "scope" }` (button may
      still show; the 403 is the guarantee) (step 6).
- [ ] Sidebar/console updates without reload when the share list changes —
      **owner-side only** (nav panel + popover via `tokens-changed`). Guest side
      needs a reload (see step 6 drift).
- [ ] Revocation denies the guest — **at request time**: new fetches 403/404,
      gone on reload. Not a live on-screen eviction (steps 7–8).

## Known v0 limitations (spelled out)

- **Tokens don't survive a plugin restart.** Token/share state is in-memory
  only; on plugin reload every token is gone and **all guest URLs are
  invalidated** (SPEC §"Data model"). The *worker deployment record* does
  persist in `bb.storage.kv`, so the worker itself can be reused across a
  restart — but with no tokens, no guest can authenticate.
- **Worker self-destructs 60 min after deploy if unclaimed.** CF temp accounts
  have a hard 60-minute TTL with no extend endpoint. Redeploy makes a **new**
  `*.workers.dev` URL and invalidates old guest URLs. The `claim.url` (surfaced
  in the owner nav panel) lets the owner claim the worker into a real CF account
  so the URL becomes stable — v0 does **not** track claim state; it just nudges
  (spike 01 + SPEC §"Worker lifecycle").
- **Guest sees `thread_id`, not the thread title.** The RPC contract exposes no
  thread title, so the nav panel and guest sidebar show the raw id (issue 16).
  A friendlier name needs a thread-lookup method the v0 contract doesn't have.
- **Copy-URL only works for session-minted tokens.** `listTokens` never returns
  the raw bearer (only its HMAC is persisted — correct posture), so the guest
  URL is only recoverable for tokens minted **in the current session** (cached
  in a `tokenId → url` map). For pre-existing tokens the Copy-URL button is
  disabled with a "re-mint needed" tooltip rather than fabricating a URL
  (issue 16).
- **Guest-side plugin frontends are suppressed.** `/api/v1/plugins` returns
  `{ plugins: [] }` for guests in v0 — no plugin UI loads guest-side (SPEC
  non-goal; issue 09).
- **No presence UI, no transcript attribution.** No "N guests reading" badge,
  guest count untracked; guest-typed messages are indistinguishable from the
  owner's in the transcript (SPEC non-goals).
- **`keybindings`-adjacent fields remain in `/system/config`.** The filter
  strips exactly `aiServices`, `keybindings`, `voiceTranscriptionEnabled`. It
  **keeps** `defaultKeybindings` and `keybindingOverrides` (the ticket named
  only `keybindings`), and keeps in-scope projects' `sources` (the guest is
  authorized for those projects and the SPA needs `sources` to render them).
  Both documented in issue 09's answer for a future review.
- **Revocation is pull-based, not a live eviction.** See steps 7–8: no proactive
  socket close on share/token removal; enforcement is at the next request. Fine
  for v0's threat model (local-trust, short sessions), worth tightening later.
- **Realtime scope is fixed at WS-upgrade time.** A share added mid-session
  doesn't flow to an already-open guest socket until reconnect/reload (step 6).

## Troubleshooting

**Where the logs live:**

- Plugin backend: `bb plugin logs shared` — `bb.log` output from `server.ts`,
  the token store, authz, and the worker lifecycle service.
- Worker-side: `wrangler tail <worker-name>` (script name `bb-shared-worker`)
  against the deployed worker, if you have wrangler pointed at the (claimed) CF
  account. On an unclaimed temp account you have no dashboard/tail access — rely
  on plugin-side logs + the `getWorkerStatus` pill.

| Symptom | Likely cause | Diagnose / fix |
|---|---|---|
| **Every guest request 403**, even a plain thread view with a valid `write` token | Plugin-id mismatch — the worker's authz URL doesn't match the plugin's mount id `shared`, so authz is unreachable and the gate fails **closed**. Ticket 22 aligned both to `shared`; a regression would reintroduce this | Run `bb plugin list` for the real id (expect `shared`); curl the authz route at `.../plugins/shared/http/authz` with `Bearer $(bb plugin token shared)` — a 200 confirms the mount. Confirm the worker's `AUTHZ_ENDPOINT_PATH` uses the same id. |
| First **mint hangs or errors** | No CF egress, or PoW/provision failure | Confirm reachability to `api.cloudflare.com`; watch `bb plugin logs shared` for the provision/upload error; `getWorkerStatus` pill shows the error state. |
| Worker was live, now **all guests 503** with `x-bb-tunnel-offline: 1` | `SharedTunnel` not connected to `/__tunnel` (dropped, or secret mismatch) | Check `getWorkerStatus.tunnel`; `stopped` is actionable. Repair the local tunnel first. Use **Recreate worker** only when deliberately replacing the worker. |
| **Guest chrome still shows** Settings / Extensions / New-thread | Chrome shim didn't inject | Confirm the guest response is `text/html` and `<html>` carries `data-bb-guest="1"`; if a bb upgrade moved a selector, run `node scripts/check-chrome-selectors.mjs <bb>/apps/app/dist` — a MISSING probe means the selector drifted and must be re-pinned (bump `BB_VERSION`). |
| **Guest sidebar shows extra threads/projects** | Response filter or authz scope wrong | Inspect the guest's `sidebar-bootstrap` response; confirm authz returns the right `thread_scope`/`project_scope` for the token (issue 19 added `project_scope`). |
| Worker **Offline** after a temporary-account failure | The saved endpoint no longer answers the exact worker identity probe | The record is retained and periodically retried. If recovery is not expected, use **Recreate worker** and tell users copied links still point to the old hostname. |
| Guest **send silently does nothing** on a `write` thread | Send blocked upstream | Check the network tab for `403 { error: "scope" }` — if present, the share is `read` not `write`, or authz denied (re-check plugin-id drift). |
| **`getWorkerStatus` shows "not deployed"** after a mint | Lifecycle stub or deploy never ran | If `mintToken` didn't await `ensureDeployed()` (or errored before it), no deploy happened — check logs. Note: opening the share popover alone does **not** deploy (drift note under "Deploy worker"). |
